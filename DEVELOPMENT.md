### November 5, 2026 - Link Hover and Focus

**Changes:**
- `web/src/index.css` - text links now get a thicker underline (2px instead of the browser's thin one) on hover, and the same underline plus a 2px clay ring (`--link`, 2px from the text, slightly rounded) on keyboard focus. Browser checks found that plain text links didn't visibly change on hover, only the cursor did: the email, "View my resume!" and Publications title on the About page, "View code ↗", "Visit ↗" and "Read the paper ↗" on project pages, and links inside write-ups. The color stays `--link`, so contrast is unchanged: 5.31:1 on the background and 5.69:1 on cards in light mode, 8.90:1 and 8.09:1 in dark mode, all above WCAG AA's 4.5:1. Shifting to the brighter `--accent` was ruled out because it's only 3.83:1 on the light background. The ring matches the one the project cards, theme switch, photo stack and home page links already use. Both rules are wrapped in `:where()` so they have no specificity, and every link with its own hover or focus style keeps it (checked in the browser: the home page links and project cards are unchanged). Links that had only the browser's default focus outline (navbar, name, footer, "← All projects", "Next project") now show the clay ring instead, so focus looks the same across the site. There's no transition: the browser's default underline thickness (`auto`) can't animate, and setting a fixed resting thickness to make it animate would change how every link looks at rest.

**Results:**
- Build and lint pass. In headless Chrome at 1280px and 390px, in light and dark mode, hovering the About page links and the wrmXpress page links (including the write-up's journal link) thickens their underline without changing color, and Tab shows the ring and thicker underline on each. Comparing every link's hover and focus styles against `main` on the home, About, Projects and wrmXpress pages, nothing else changed except the focus ring on links that only had the browser's default. No project has a live link yet, so "Visit ↗" wasn't seen, but it's in the same `.projectLinks` row as "View code ↗" and gets the same rules.

### November 4, 2026 - Lighthouse Fixes, Going Live and Moving to GitHub Pages

**Changes:**
- `.github/workflows/pages.yml`, `.github/workflows/deploy.yml`, `infra/` - the site moves from AWS (S3 + CloudFront) to GitHub Pages, at ankitjk.com. I don't want to pay for hosting, and since this repo is public, GitHub Pages is free; it's also made for a static site like this one. ankitjk.com turned out to be mine after all (at Porkbun), so the site gets its domain now too: I'm pointing its DNS at GitHub Pages myself (A/AAAA records for the bare domain, `www` as a CNAME to ankitjk.github.io, plus GitHub's domain verification), and the domain is entered in the repo's Settings → Pages after the first deploy rather than through a CNAME file. The repo's Pages source is set to "GitHub Actions". The new workflow is GitHub's standard Pages flow: on every push to `main` (or by hand), a build job runs `npm ci` and `npm run build` and uploads `web/dist`, then a deploy job publishes it to the `github-pages` environment. Each action is pinned to its current major version (checked with `gh api repos/<owner>/<repo>/releases/latest`): checkout v7, setup-node v7, configure-pages v6, upload-pages-artifact v5, deploy-pages v5. `deploy.yml` and the CloudFormation template in `infra/` are deleted; they stay in the repo's history. What's traded off: GitHub Pages caches every file for 10 minutes, so the hashed files in `assets/` no longer get a year-long cache and a change can take up to 10 minutes to reach someone who visited recently; and it allows no custom headers, so the security headers CloudFront added are gone. The live AWS stack `ankitjk-site` and the GitHub repo variables `AWS_ROLE_ARN`, `S3_BUCKET` and `CLOUDFRONT_DISTRIBUTION_ID` aren't touched here; they'll be removed by hand once the Pages site is live.
- `web/vite.config.ts`, `web/src/data/pages.ts`, `web/src/pages/Home.tsx`, `web/src/pages/About.tsx`, `web/src/pages/Projects.tsx`, `web/src/pages/Project.tsx`, `web/src/pages/NotFound.tsx`, `web/src/main.tsx`, `web/index.html` - every page address is now a real file. GitHub Pages has no rewrite rules, so it can't send `/about` to `index.html` the way the CloudFront Function did for react-router's BrowserRouter; without this, opening any page but the home page directly would show a 404. A small Vite plugin in `vite.config.ts` writes a copy of the built `index.html` for each page once the build is done: `about.html`, `projects/index.html`, `projects/<slug>.html` for every project in `projects.ts`, and `404.html`, which GitHub Pages sends with a real 404 status for any address that doesn't exist, and where the app shows its "Page not found" page. GitHub Pages serves `/about` from `about.html` directly, while `about/index.html` would make `/about` redirect to `/about/` first, so pages are `<address>.html`. Projects is the exception, since the project pages need a `projects/` folder and `projects.html` next to that folder could be read either way; so `/projects` is the one address that redirects, to `/projects/`, which react-router treats the same. Each copy carries that page's own title, description, `og:title` and `og:description`, so link previews and search engines that don't run JavaScript see the right text, which covers most of what was left open below. The titles and descriptions moved out of the page components into `web/src/data/pages.ts`, which both the pages and the build read, so there's one place to change them; the text itself is unchanged. The plugin stops the build if `index.html` loses its `<title>` or description, so the pages can't quietly all end up with the same text. `main.tsx` still removes the page's description from the HTML when the app starts, since React adds its own alongside it; the `og:` tags stay, since only link previews read them. No new dependencies.
- `infra/site.yaml`, `infra/README.md` - the deploy role now trusts the subject GitHub actually sends. The first run of the deploy workflow failed at signing in to AWS ("Not authorized to perform sts:AssumeRoleWithWebIdentity") because the role required the subject `repo:ankitjk/personal-website:ref:refs/heads/main`, but this repo uses GitHub's immutable subject claims, which add the owner's and repo's numeric IDs: `repo:ankitjk@43698143/personal-website@1443449982:ref:refs/heads/main` (confirmed with `gh api repos/ankitjk/personal-website/actions/oidc/customization/sub` and GitHub's OIDC docs). The `GitHubRepo` parameter is replaced by `GitHubSubjectPrefix`, defaulting to `repo:ankitjk@43698143/personal-website@1443449982`, with a comment on where the value comes from and a pattern that rejects the old name-only form. The check is still an exact `StringEquals` on the subject plus the audience, rather than a wildcard, and immutable subjects stay on, since they're safer: a repo deleted and made again with the same name gets new IDs and can't deploy. The role keeps its logical ID and name, so updating the stack changes its trust policy in place. The IDs aren't secret. `infra/README.md`'s Notes now show the exact subject and how to look up the prefix if the repo ever moves.
- `infra/site.yaml`, `infra/README.md` - the domain is now optional, so the site can go live at its CloudFront address (like `d1234abcd.cloudfront.net`) before I have a domain. I don't control ankitjk.com yet, so the first deploy waited forever at the certificate (ACM can't validate a domain whose DNS I can't edit) and had to be deleted. `DomainName` now defaults to empty, and without it the stack makes no certificate, gives the distribution no extra addresses, uses CloudFront's own certificate (which can't have a minimum TLS version set, so that setting is only used with a domain), and skips the www redirect while still serving `index.html` for page addresses. The function stays one piece of code that only redirects when there's a domain, rather than two copies chosen between, so there's one version of the page-address rule to keep right. With a domain the stack is the same as before: rendering the template both ways and comparing with the old one, the only differences are the outputs and that check in the function. Every resource keeps its name in the template, so adding a domain later updates the bucket, distribution and role in place rather than replacing them, and the GitHub variables don't change. New `SiteUrl` output (the CloudFront address, or the domain once there is one) and a `WwwUrl` output that only exists with a domain. `infra/README.md` now explains the two ways to deploy: first-time setup without a domain (no Porkbun steps), and a new "Adding a domain" section that re-runs the deploy with `DomainName=ankitjk.com`, then validates the certificate and points DNS at CloudFront as before, including what happens if that update fails (the stack goes back to no domain and the site keeps working). `deploy.yml` and the site's code don't mention the domain, so they're unchanged.
- `infra/site.yaml`, `infra/README.md`, `.github/workflows/deploy.yml`, `CLAUDE.md` - AWS hosting, written but not deployed yet. One CloudFormation stack in us-east-1 (a new AWS account, and CloudFront only takes certificates made there) holds a private, encrypted S3 bucket that only the CloudFront distribution can read (via Origin Access Control), the certificate for ankitjk.com and www.ankitjk.com, the distribution (HTTPS only, TLS 1.2+, HTTP/2 and 3, the cheapest price class, AWS's managed caching and security-headers policies), a monthly cost budget that emails an address given at deploy time so it never lands in this public repo, and a role GitHub Actions can use. DNS stays at Porkbun rather than moving to Route 53, so the certificate is validated by adding its CNAME records at Porkbun by hand while the stack waits; `infra/README.md` walks through that and the rest of the first deploy in order. After review it also covers how to sign in to AWS safely (an IAM Identity Center user or CloudShell, never root access keys), that brand-new accounts may need a free support case before they can create CloudFront distributions, and how to recover when the first create rolls back (delete the stack and run it again, keeping the Porkbun validation records). A small CloudFront Function redirects www to the bare domain and serves `index.html` for page addresses like `/about`, since the site uses react-router's BrowserRouter; missing files get a real 404 showing the site's "Page not found" page. No Content-Security-Policy header, because a strict one would block the inline dark-mode script in `index.html`. The workflow deploys on every push to `main`, signing in to AWS with GitHub's short-lived tokens (OIDC) rather than stored keys; the role only works for this repo's `main` branch and can only upload to the bucket and clear the CloudFront cache. Hashed files in `assets/` are cached for a year, everything else is checked on each visit. The workflow skips itself until the GitHub repo variables are set, so merging before the stack exists doesn't produce a failing run. CLAUDE.md now lists `infra/` and `.github/workflows/`.
