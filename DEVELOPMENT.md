## Changelog

### November 4, 2026 - README Update, robots.txt and Agent Definitions

**Changes:**
- `infra/site.yaml`, `infra/README.md` - the domain is now optional, so the site can go live at its CloudFront address (like `d1234abcd.cloudfront.net`) before I have a domain. I don't control ankitjk.com yet, so the first deploy waited forever at the certificate (ACM can't validate a domain whose DNS I can't edit) and had to be deleted. `DomainName` now defaults to empty, and without it the stack makes no certificate, gives the distribution no extra addresses, uses CloudFront's own certificate (which can't have a minimum TLS version set, so that setting is only used with a domain), and skips the www redirect while still serving `index.html` for page addresses. The function stays one piece of code that only redirects when there's a domain, rather than two copies chosen between, so there's one version of the page-address rule to keep right. With a domain the stack is the same as before: rendering the template both ways and comparing with the old one, the only differences are the outputs and that check in the function. Every resource keeps its name in the template, so adding a domain later updates the bucket, distribution and role in place rather than replacing them, and the GitHub variables don't change. New `SiteUrl` output (the CloudFront address, or the domain once there is one) and a `WwwUrl` output that only exists with a domain. `infra/README.md` now explains the two ways to deploy: first-time setup without a domain (no Porkbun steps), and a new "Adding a domain" section that re-runs the deploy with `DomainName=ankitjk.com`, then validates the certificate and points DNS at CloudFront as before, including what happens if that update fails (the stack goes back to no domain and the site keeps working). `deploy.yml` and the site's code don't mention the domain, so they're unchanged.
- `infra/site.yaml`, `infra/README.md`, `.github/workflows/deploy.yml`, `CLAUDE.md` - AWS hosting, written but not deployed yet. One CloudFormation stack in us-east-1 (a new AWS account, and CloudFront only takes certificates made there) holds a private, encrypted S3 bucket that only the CloudFront distribution can read (via Origin Access Control), the certificate for ankitjk.com and www.ankitjk.com, the distribution (HTTPS only, TLS 1.2+, HTTP/2 and 3, the cheapest price class, AWS's managed caching and security-headers policies), a monthly cost budget that emails an address given at deploy time so it never lands in this public repo, and a role GitHub Actions can use. DNS stays at Porkbun rather than moving to Route 53, so the certificate is validated by adding its CNAME records at Porkbun by hand while the stack waits; `infra/README.md` walks through that and the rest of the first deploy in order. After review it also covers how to sign in to AWS safely (an IAM Identity Center user or CloudShell, never root access keys), that brand-new accounts may need a free support case before they can create CloudFront distributions, and how to recover when the first create rolls back (delete the stack and run it again, keeping the Porkbun validation records). A small CloudFront Function redirects www to the bare domain and serves `index.html` for page addresses like `/about`, since the site uses react-router's BrowserRouter; missing files get a real 404 showing the site's "Page not found" page. No Content-Security-Policy header, because a strict one would block the inline dark-mode script in `index.html`. The workflow deploys on every push to `main`, signing in to AWS with GitHub's short-lived tokens (OIDC) rather than stored keys; the role only works for this repo's `main` branch and can only upload to the bucket and clear the CloudFront cache. Hashed files in `assets/` are cached for a year, everything else is checked on each visit. The workflow skips itself until the GitHub repo variables are set, so merging before the stack exists doesn't produce a failing run. CLAUDE.md now lists `infra/` and `.github/workflows/`.
- `.claude/agents/builder.md`, `.claude/agents/reviewer.md`, `.claude/agents/site-checker.md`, `CLAUDE.md` - three reusable agents, so each brief no longer has to repeat the same instructions. The builder turns one task into one pull request in its own worktree. The reviewer and site-checker are read-only, so checking stays separate from building: the reviewer judges a pull request against its task and CLAUDE.md and is given the change, not the builder's reasoning, so it doesn't just agree with it; the site-checker carries the browser rules worked out so far (light and dark, desktop and phone, never click mailto links, Lighthouse on a production build). Chosen over agents that message each other (backend, frontend, testing, QA): the site is small and static with no backend, its tasks are independent, and each extra hand-off costs tokens and loses detail. Worth revisiting if the site gains a backend. CLAUDE.md lists the three and when each runs.
- `web/src/pages/Home.tsx`, `web/src/pages/About.tsx`, `web/src/pages/Projects.tsx`, `web/src/pages/Project.tsx`, `web/src/pages/NotFound.tsx`, `web/src/main.tsx` - each page now has its own meta description, which search engines can show under the page's title, because the Lighthouse audit flagged every page as sharing index.html's one generic description. The pages already had their own titles, which are unchanged. It uses React 19's built-in support for `<title>` and `<meta>` inside components (React moves them into `<head>`) rather than adding a library such as react-helmet. Each project's page reuses the project's one-line `description` from `projects.ts`, and the 404 page reuses "That page doesn't exist.". The About description is in my own words, listing all five areas I work in rather than a shortened three. The Home and Projects descriptions are new drafts in my voice, built only from what's already on the site, to be rewritten. index.html keeps its description for anything that reads the page without running JavaScript; `main.tsx` removes it once the app starts, since React adds a page's description alongside it rather than replacing it, and two descriptions would leave search engines using the generic one.
- `web/src/assets/photos/`, `web/src/data/photos.ts`, `web/src/components/PhotoStack.tsx` - the About page photos are now lighter to download, as the Lighthouse audit suggested ("properly size images"). Measured in Chrome, the stack shows each photo 220px wide (210px inside its border) at both 1280px and 390px wide, yet every screen downloaded the 800px files (239 KB for all three). Each photo now also comes in 220px and 440px copies, made from the 800px files (the originals aren't in the repo) with `cwebp -metadata none` and checked with `webpinfo`, and the browser picks one with `srcset`/`sizes`: normal screens get the 220px files (30 KB for all three), 2x screens and Lighthouse's phone get the 440px ones (85 KB), and 3x phones still get the 800px ones so they stay sharp. The stack looks and moves the same.

**Minor:**
- `README.md` - brought up to date with the site, since it still described the starter project: photos are now listed as living in `web/src/assets/photos/` (via `web/src/data/photos.ts`) rather than `web/public/`, the project write-ups in `projects.ts` are explained (`why`/`what`/`how` paragraphs, `[text](url)` links, `tags` on the card versus `tech` on the project's page), it says plainly that the site isn't online yet, and a new "Making changes" section says every change goes through a pull request only Ankit merges, pointing to CLAUDE.md for the details.
- `web/public/robots.txt` - added, allowing search engines to read the whole site. A Lighthouse audit (all pages 100 for performance, accessibility and best practices, in light and dark mode) found it was the only failure: without the file, asking for `/robots.txt` returned the site's own page, which search engines can't read, costing the SEO score (91-92). The audit's other suggestions (smaller About photos, per-page descriptions, a softer home page fade-in) were left for later.
- `web/src/pages/Home.module.css` - softer home page fade-in, as the Lighthouse audit suggested. The name and line used to start fully transparent, and the browser doesn't count text as shown while it's invisible, so Lighthouse scored the page's main content (the line under the name on phones, the name on desktop) as appearing only once the fade got going ("element render delay"). The entrance now starts at 40% opacity and 0.4rem low instead of invisible and 0.75rem low, and is shorter (0.5s instead of 0.7s, the links' delay 0.08s instead of 0.12s), so it still settles in gently but the content shows from the first frame. In Lighthouse on a production build, the time until the main content shows (Largest Contentful Paint) went from about 1.8s to 0.76s on phones and 0.40s to 0.21s on desktop, now the same moment as the first paint; the performance score was already 100 and stays there. Reduced-motion visitors still get no animation.

**Left open:**
- Link previews (Open Graph tags, used when a link is shared in a message or post) and search engines that don't run JavaScript still only see index.html's title and description, since the site is a single-page app that builds each page in the browser. Fixing that would mean pre-rendering each page into its own HTML file at build time, a separate decision.
